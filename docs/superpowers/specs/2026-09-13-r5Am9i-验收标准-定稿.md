## ⚠️ 先看一个关键发现：「仓库已有分级重试」这句只对了一半

事项描述写：
> 【原文】重试分级：只重试网络 / 429 / 5xx / 超时，**不重试 4xx**；指数退避 + jitter（500ms~1s 起，上限 16~30s，2~3 次）。仓库已有分级重试退避（`hub/llm/client.py:31-32,121`），**不要重写**

**实测 `hub/llm/client.py` 的实现**：

```python
MAX_RETRIES = 3            # :31
BACKOFF_BASE_SECONDS = 1.0 # :32

for attempt in range(self._max_retries + 1):        # :119
    if attempt > 0:
        self._sleep(self._backoff_base * (2 ** (attempt - 1)))  # :121 指数退避 ✅
    try:
        result = self._call_once(...)
        return result
    except LLMError as e:                            # :130
        last_error = e                               # ← 无条件吞下并继续重试
```

对照事项要求，逐项判定：

| 要求 | 现状 | 结论 |
|---|---|---|
| 指数退避 | `base * 2^(attempt-1)` | ✅ **已有** |
| **分级**（4xx 不重试） | `except LLMError` **无条件重试所有错误** —— 包括 `LLM_AUTH_FAILED`（401）、`LLM_SCHEMA_INVALID` | ❌ **没有**，且会重试 401 —— **这是个缺陷，不是「已具备」** |
| jitter | 无 | ❌ 没有 |
| 起始 500ms~1s | `BASE = 1.0` | 🟡 勉强合规（1.0s） |
| 上限 16~30s | 最大等待 = `1.0 × 2^(3-1)` = **4s** | ❌ 达不到要求上限 |
| 2~3 次 | `MAX_RETRIES = 3` | ✅ 合规 |

**所以「不要重写」要理解为「复用它的退避骨架与可测性设计」，而不是「它已经满足要求」。**

**它的可复用之处（值得保留）**：
- `sleep_fn` 依赖注入（`self._sleep = sleep_fn`）→ **测试可注入假时钟，不会真等** —— 这是很好的可测性设计，新实现要沿用
- `LLMError` 带 `error_code` + `retry_count` → 错误分类的骨架已有

**建议的做法**（待 owner 确认）：
1. 抽出**共用的退避策略**（建议 `hub/domain/retry.py`，纯函数零 IO，符合项目「纯函数域」惯例）
2. **MCP 层用新策略**
3. **顺势修正 `hub/llm/client.py` 的无条件重试**（至少做到「不重试 401 / 4xx」）—— ⚠️ 这会改变 LLM 路径行为，**需要单独的测试覆盖**，不能顺手改

## 一、重试分级 · 验收标准

### 必须满足（每条都能写成一条测试）

| # | 验收标准 | 怎么测 |
|---|---|---|
| R1 | **4xx 不重试**：任何 4xx 响应，**只尝试 1 次** | 注入返回 400 / 401 / 403 的桩，断言调用计数 == 1 且立即失败 |
| R2 | **429 要重试** | 注入「第 1 次 429、第 2 次成功」→ 断言最终成功且总尝试 2 次 |
| R3 | **5xx 要重试** | 同上，用 500 / 502 / 503 |
| R4 | **网络错误要重试** | 注入连接异常 → 断言重试发生 |
| R5 | **超时要重试** | 注入 timeout → 断言重试发生 |
| R6 | **重试次数上限 2~3 次** | 全程失败 → 断言总尝试次数 == `上限 + 1`，且最终抛出**带分类的错误**（不是裸异常） |
| R7 | **退避是指数且带上限** | 用**注入的假 sleep** 记录每次等待时长 → 断言：单调递增、且**任何一次 ≤ 30s** |
| R8 | **有 jitter**（相邻等待不等长） | 【推断】同一输入跑两次，等待序列**不应完全相同**；且 jitter 不得让等待越界（仍 ≤ 上限） |
| R9 | **假 sleep 注入可用** | 测试**不真的等待**（用注入的 `sleep_fn`，断言总测试耗时 < 1s） |
| R10 | **错误分类可辨识** | 抛出的错误能区分「4xx 类（不重试）」与「已重试耗尽」两种 —— 调用方能据此决定是否降级 |

### 不算做完的情况
- ❌ 只加退避、没有分级（现状就是）
- ❌ 分级靠**字符串匹配错误消息**而不是结构化 `error_code`
- ❌ 测试里真的 `time.sleep`（会拖慢全量套件，且不可控）

## 二、REST 降级通道 · 验收标准

### 背景（事项原文）
> 【原文】REST 降级通道：MCP 不可用时直接走 HTTP API，复用同一套 Pydantic 模型。**这是唯一不需要宿主配合的通道，优先级高于 MCP 本身**

### 必须满足

| # | 验收标准 | 怎么测 |
|---|---|---|
| D1 | **MCP 不可用时能走通** | 让 MCP 端点不可达（桩），断言降级通道仍返回**成功结果** |
| D2 | **返回结构一致** | 同一输入，MCP 通道与降级通道的返回**字段集合完全相同**（用同一份 Pydantic 模型校验，两边都过） |
| D3 | **模型单一事实源** | 两条通道**引用同一组** Pydantic 模型（不是各写一份）—— 断言方式是「改一处、两边同时生效」 |
| D4 | **降级是显式可观测的** | 【推断】响应里应能看出「本次走的是降级通道」（字段或日志），否则事后无法判断请求走的哪条路 |
| D5 | **不需要宿主配合** | 【推断】降级通道必须是**纯 HTTP**，不依赖任何 MCP 客户端能力（这正是它优先级更高的原因） |
| D6 | **4xx 不降级** | 【推断】如果失败是 4xx（客户端错），**不该降级重试** —— 降级是应对「通道不可用」，不是应对「请求本身错」 |

### 不算做完的情况
- ❌ 降级通道返回的是「另一套结构」（哪怕语义相同）—— 那就没做到 D2/D3
- ❌ 只在文档里写了降级方案，代码里没有可执行入口
