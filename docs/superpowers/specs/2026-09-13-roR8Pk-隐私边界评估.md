# roR8Pk · 隐私边界评估（n=2–5 人）

范围：`mcp-decision-hub` 仓库当前代码。所有结论均附 `文件:行号` 证据；行号以评估当日的
工作树为准。配套可测用例：`tests/domain/test_stance_privacy.py`（3 人 2 轮局）。

---

## 1. 跨轮聚合反推（核心）

**现状**

- LLM 轮次摘要（`RoundSummary`）的 schema 本身**不带身份**：只有
  `consensus_points / divergences / blind_spots / open_questions / convergence`
  五个字段（`hub/db/models.py:141-159`），外发载荷同样只有这五项
  （`hub/api/pipeline.py:150-157` `_summary_to_dict`；`hub/mcp_server/methods.py:394-401`
  `_summary_payload`）。喂给 LLM 的输入也做了白名单裁剪，只带
  `answers / notes`，不带 username/id（`hub/api/pipeline.py:119-129`
  `_submissions_for_llm`）。
- **但是**，与摘要并列存在的立场读接口把「逐人逐轮立场 + 身份」直接公开给
  全体事项成员：`list_stances` 返回该事项**全部轮次、全部参与人**的 Stance 行
  （`hub/api/stances.py:307-316`），出参 `StanceRead` 含
  `user_id / round_number / stance / confidence / position_summary / created_at`
  （`hub/schemas/stance.py:85-111`）；`get_stance` 可按任意 `target_user_id`
  定向读（`hub/api/stances.py:279-304`）。成员闸门只挡非成员
  （`hub/api/stances.py:193-202`，404 文案统一）。
- 另有若干小型身份泄露面：`analyze_round` 的出参 `skipped_user_ids` 把脏数据行的
  user_id 经 `asdict` 直接外发给任何成员（`hub/api/stances.py:181-190` +
  `hub/web/routes_api.py:49`）；收敛降级审计 `CONVERGENCE_DEGRADED` 的 detail 带
  `user_id`（`hub/api/stances.py:160-165`）。

**「摘要只带内容、不带身份，2→1 还能否反推？」—— 分层回答**

- 只看 `RoundSummary` 五字段：不能。没有计数、没有身份、没有时间戳，
  「2 人 oppose → 1 人 oppose」这个差分输入在摘要层根本不存在。
  （配套测试 `test_round_summary_payload_carries_no_identity` 为绿，固化此事实。）
- 但「公开摘要视图」在**当前实现里不止 RoundSummary**：`GET /api/items/{id}/stances`
  把逐人逐轮立场连同 `user_id` 一起给了每个成员。在这个真实公开面上，
  反推甚至不需要「差分」技巧——直接按轮次分组读 `user_id` 集合即可：
  round1 oppose={alice,bob}、round2 oppose={alice}，bob 是唯一改动者，**唯一确定**。
  所以「只存 content_hash 挡不住逐轮差分」的担心在当前代码面前是**降级**的说法：
  现状是连差分都不必做，身份是直给的。
- 残余风险：即使把逐人立场收回，`divergences` 等 LLM 自由文本仍可能点名
  （输入裁剪只保证不喂 id，不保证模型不复述内容里的身份线索）；而出口扫描
  `scan_view` 只扫 `build_audience_view` 的 sections（`hub/domain/audience.py:139-185`），
  **从不扫 RoundSummary 文本**。这是摘要层唯一未被覆盖的身份回漏通道。

**结论**：在 2–5 人下**失效（是）**。当前公开面（逐人立场列表）使轮间改动者可被
唯一确定，配套测试按设计为红。

**建议**

- 成员可见粒度降级：成员只见「按轮聚合计数」且加 k-匿名阈值（反对/支持计数在
  n<3 的桶里不公开）；逐人立场仅本人 + 发起人可见，或延后到事项终态再公开。
- 「加噪声」的代价：立场是收敛判定的输入（`hub/api/stances.py:153`
  `evaluate_convergence_lenient`），在存储层加噪会污染收敛判定与阻断逻辑
  （`hub/domain/convergence_eval.py:167-173` 的 0.7 硬阻断），不可接受；只能在
  **展示层**加噪，而展示层加噪对 2–5 人的小样本差分几乎无效（噪声幅度要 ≥1 人，
  等于直接隐藏计数）。**「延后公开」代价更可控**：牺牲过程中透明度，保留终局
  可审计性。推荐后者 + 聚合阈值。
- 摘要层补一道对 RoundSummary 文本的身份扫描（复用 `_ID_SHAPED` 思路），堵住
  LLM 自由文本回漏。

**判定标准**：`tests/domain/test_stance_privacy.py` 中
`test_public_view_does_not_allow_identifying_stance_changer` 由红转绿——
3 人 2 轮局里，观察者从成员可见视图**无法**唯一确定轮间改动者。

## 2. confidence 字段本身是泄露面

**现状**：`confidence` 为原始 float 存储（`hub/db/models.py:230`），经 `StanceRead`
原值外发（`hub/schemas/stance.py:95`），list/get 两个读接口都对全体成员开放
（`hub/api/stances.py:279-316`）。同时它是收敛判定的硬阻断输入：
`confidence >= 0.7` 的 oppose 直接阻断收敛（`hub/domain/convergence_eval.py:22,167-173`）。
于是观察者把「某人的 confidence 原值」与「事项 blocked / 未收敛」对照，即可反推
谁在用高置信度卡结论。

**结论**：**失效（是）**。原值外发 + 公开语义（0.7 门槛写在代码里）= 双向泄露。

**建议**：外发层分档（如 low/mid/high 三档）或 confidence 仅本人可见；收敛判定
继续用原值（内部），出参走分档映射。

**判定标准**：`StanceRead` 不再出现原始 float；测试断言外发值落在固定档位集合内，
且无法从外发值恢复 `>= 0.7` 的精确边界。

## 3. 读取侧没有任何审计

**现状**：事项原文「现有只审计写操作」**部分过时**——`get_stance` 已写
`STANCE_READ` 审计（`hub/api/stances.py:299-303`，事件常量 `hub/api/audit.py:35`）。
但 `list_stances`（`hub/api/stances.py:307-316`）与 `analyze_round`
（`hub/api/stances.py:131-190`，仅写脏数据降级审计）**零读审计**；而 list 才是
批量拉取他人立场的主入口。事项原文提到的 `POST /items/{id}/ask` 端点在当前代码库
**不存在**（全库无此路由，属方案预留）。

**结论**：**部分失效**。定向单读有留痕，批量读与聚合读没有。

**建议**：`list_stances` / `analyze_round` 补 `STANCE_READ`（detail 带
round_number、返回行数）；ask 端点落地时审计为强制前置条件。

**判定标准**：对每个读接口各有一次调用 → 审计表出现对应 `stance_read` 事件且
detail 含目标/范围；配套测试已断言 list 当前审计计数为 0（红测内固化现状）。

## 4. ask 配额

**现状**：ask 端点不存在（见上）。立场层的定向提问通道是 `questions_for` 字段：
一次提交可对任意 `participant_id` 挂最多 50 条自由文本问题
（`hub/schemas/stance.py:48-54,74`），无任何频次/对象配额。限流器只覆盖
token/submit/account/login 四类键（`hub/domain/rate_limit.py:1-5,76-93`），
stance 读写均不在内。

**结论**：**失效（是，机制整体缺失）**。逐层探测底线在当前代码里没有成本上限。

**建议**：ask（或 questions_for 生效路径）按 `(matter_id, actor, target)` 滑窗配额，
复用 `RateLimiter`；超限 429。

**判定标准**：同一 actor 对同一 target 第 N+1 次定向提问返回 429 且写审计；
N 由配置决定。

## 5. ttl 的执行主体

**现状**：`Stance.ttl_seconds` 只存不执行——写入（`hub/api/stances.py:269`）、
出参回显（`hub/schemas/stance.py:107`），全库**无任何代码读取它做过期判定**
（grep 命中均为字段定义/透传）。唯一的调度器 `scan_once` 只扫 `Task.deadline_at`
（`hub/api/scheduler.py:40-83`），stances 不在扫描范围。

**结论**：**失效（是）**。过期立场静默继续参与收敛与展示，且过期后无任何主体
负责重新拉人——正是事项担心的「过期立场静默当结论用」。

**建议**：扩展 `scan_once`（或新增 stance 扫描相位）：`created_at + ttl_seconds < now`
的立场标记 expired，从 `analyze_round` 输入剔除并写审计；对过期未重表态的参与人
重新发任务（复用 `_open_followup_round` 的建任务路径）或进重分配池
（`hub/api/reassignment.py` 已有 pending/timeout 换人机制可对接）。

**判定标准**：构造 ttl=60s 的立场，时间前进后：不再出现在 `analyze_round` 输入、
出现 `stance_expired` 审计、且该参与人出现新的 pending 任务。

## 6. 跨方立场注入本地代理（XPIA）

**现状**：他人的 `position_summary / rationale_summary` 等自由文本经
list/get 接口**原文**外发（`hub/api/stances.py:279-316`；
`hub/schemas/stance.py:96-97`）。成员侧的代理若把这些字段读入本地 LLM 上下文，
即为提示注入通道。出口扫描 `scan_view` 只覆盖 `build_audience_view` 产出的
sections（`hub/domain/audience.py:139-185`，调用点仅 `hub/api/stances.py:179`），
**不扫 stance 原文出参**。注意 `analyze_round` 这条路径是安全的：确定性裁剪在先
（每人只见自己的 dissenting 原文，`hub/domain/audience.py:76-86`）、扫描在后——
注入面集中在「裸立场 API → 本地代理」这条旁路。

**结论**：**部分失效**。受控通道（audience view）防住了；裸 API 通道敞开。

**与 rsEXuh 的联动**：出口扫描是 rsEXuh 的域。本项的结论是：rsEXuh 的扫描覆盖面
需要从「audience sections」扩展到「一切会进入代理上下文的跨方自由文本出口」，
至少包括 `StanceRead` 的 `position_summary / rationale_summary / questions_for`；
或者约定「他人立场一律以引用/摘要形态入上下文，原文不进 prompt」。
**本线不改出口扫描实现**，只登记覆盖面缺口。

**判定标准**：他人立场原文进入本地代理上下文前必经统一出口（扫描或引用化包裹），
并有测试证明绕过裸 API 的路径不存在。

---

## 总结论：「不设盲区、全员可见 + 按参与人可见」在 2–5 人下是否失效

**失效。** 两层含义：

1. 数学上：n≤5 时任何按人/按轮的公开（哪怕只是聚合计数的逐轮差分）都足以
   唯一定位个人，「全员可见」与「匿名」不可兼得——这是小样本的结构性问题，
   不是实现 bug。
2. 实现上：当前代码连「聚合计数」的克制都没有，直接把逐人逐轮立场 + user_id +
   confidence 原值公开给全体成员（`hub/api/stances.py:307-316` +
   `hub/schemas/stance.py:85-111`），比事项设想的最坏情况更暴露。

落地建议的优先级：先收读接口粒度（逐人→聚合 + k 阈值 / 延后到终态），
再补读审计与配额，最后接 ttl 调度与 XPIA 出口扩展。

## 附带发现

1. `_visible` 恒为 True（`hub/api/stances.py:210-223`）——`visibility` 字段已退化
   为纯留痕（注释明确系有意修正 PRD 角色表），但 `StanceCreate`/`StanceRead` 仍
   收发该字段，对外呈「假旋钮」观感；建议文档化或在 schema 层标注。
2. `analyze_round` 出参 `skipped_user_ids` 向全体成员泄露脏数据行的 user_id
   （`hub/api/stances.py:189` + `hub/web/routes_api.py:49`）——小型身份泄露面，
   建议降级为计数。
3. HTML 详情页对发起人展示每个任务的 assignee username 与 Output 原文
   （`hub/web/routes_matters.py:132-138`），参与人只见自己（`:139-142`）——
   任务层对发起人完全不匿名，与立场层「全员可见」叠加后，发起人是事实上的
   全知方；PRD 若定位发起人为仲裁者则需在隐私声明里明示。
4. `get_stance` 查询无 `limit(1)`（`hub/api/stances.py:291-295`），依赖
   `scalar()` 取排序首行；有 `(matter_id, round_number, user_id)` 唯一约束兜底
   （`hub/db/models.py:203`），仅效率/风格问题。
5. RoundSummary 的 LLM 自由文本无身份出口扫描（扫描只覆盖 audience view），
   见第 1 条残余风险。

## 拿不准的地方

- 事项原文的 `POST /items/{id}/ask` 与「方案第五节」指向一份方案文档，当前仓库
  代码中不存在该端点；本评估对 ask 的结论基于「机制缺失」而非「实现有洞」。
  若 ask 已在其他分支实现，第 3、4 条需按实现复核。
- 「延后公开」对收敛体验的影响（成员过程中看不到彼此立场是否会降低博弈质量）
  属产品判断，超出代码证据范围。
