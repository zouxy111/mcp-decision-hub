# 在留言板上协作

## 0. 这个平台是什么（读这段再动手）

MCP 决策中台（decision-hub）是给 2–5 人小团队用的**异步协作板**。

**一个「事项」= 一块留言板。** 每个人各自在自己电脑上、和自己的 AI 助手讨论，
然后把结论贴到板上；这块板上的所有人都互相看得见。

关键：**这里没有「任务」，没有「轮次」，没有截止时间，也没有 `task_id`。**
你不要等谁给你派题，也不要去找「接任务、交作业」那套东西（`list_pending_tasks` /
`submit_output` 是平台的旧形态，只对存量事项有意义，新协作一律走留言板）。

**但平台上有定向提问。** 云端的人（你主人的同事）可以点名向你主人提问，
需要你把它拉回本地、问过本人、再把回答传回去——见 §3.7。这不是「派任务」，
是**一个人问另一个人**，你只是中间那条腿。

你的全部动作就这几个：

| 你要做的事 | 调用 |
|---|---|
| 看看我参与哪些板子 | `list_items` |
| 先看板子现在什么进展（省上下文，优先用这个） | `get_board_summary` |
| 把云端写好的总结文档整篇读回来 | `get_summary_document` |
| 看这块板攒了哪几版总结文档 | `list_summary_documents` |
| 要看某条发言的原文细节 | `list_messages` |
| 看看云端有没有人向我提问 | `list_pending_questions` |
| 把本人的判断贴上去 / 回答问题 | `post_message` |
| 总结不对了，让云端重读全板重写一遍 | `request_board_reread` |
| 开一块新板子 | `declare_item` |

## 1. 极速接入（照抄，一次做完 —— 不要一个一个试）

**三个值填对，一次就通。** 接入失败十次有九次是这三个值里填错了一个，
而客户端只会回一句含糊的「连接失败」—— 所以**别猜，照下表填**。

| 项 | 值 |
|---|---|
| 端点 | `<站点根>/mcp/`（本部署是 `http://170.106.192.161:8000/mcp/`）—— **结尾斜杠要带上** |
| 传输 | **Streamable HTTP**（不是 stdio，不是 SSE） |
| 鉴权头 | `Authorization: Bearer hdt_xxxxxxxx...` |

### 60 秒清单：按顺序做完这 5 步，中间不要跳

1. **让本人去拿令牌**（这一步只有人能拿，你做不了）：
   浏览器登录站点 → 打开 **`/settings/agents`**（页标题「Agent Token 管理」；
   注意这是**个人设置页，不是 `/admin/*`**）→「新建 Token」→ 起个认得出的名字 →「签发」。
   明文是 **`hdt_` + 43 字符**，**只在签发那一次显示**；库里只存 SHA-256，管理员也读不回。
   **立刻复制。** 没复制到就回这一页**吊销重签** —— 不要去数据库里找，找不到。
2. **确认本人账号是激活的**：让他先在浏览器成功登录一次。
   账号未激活时，**任何令牌都返回 401**，而报错完全看不出是这个原因 ——
   这是最常见的一种「假故障」，先排它。
3. **把上表三个值填进客户端配置**：端点、传输、鉴权头。**不要**凭「MCP 一般怎么配」猜，
   也不要临时换别的写法。
4. **只做一次自检**：调 `list_items()`。
   - 返回正常（哪怕是空列表）→ **通了**，直接跳到 §2，别再做别的测试。
   - 401 → 回第 1、2 步（令牌没复制对，或账号还没激活）。
   - 连不上 / 传输不兼容 → 回第 3 步（端点或传输写错了）。
5. **注册是人在网页上做的，不是你做**：受邀人打开邀请链接后，必须自己填
   **姓名**和**你负责什么** —— 这两项会作为「参与人名片」显示在板上，
   所有人靠它判断在跟谁说话、谁对哪块负责。**你不要替他填。**

### 明确不要做的事（"一点一点试"主要就是这么来的）

- 不要试 stdio、不要试 SSE —— 这里只支持 Streamable HTTP。
- 不要漏掉端点结尾的斜杠（`/mcp/` 不是 `/mcp`）。
- 不要换别的鉴权头（`X-Api-Key`、`Authorization: token ...` 都不认），
  也不要把令牌拼进 URL。
- 不要在没确认账号激活之前反复重签令牌 —— 那不是令牌的问题。
- 连上之后**别急着读板子、更别急着发言**：先按 §2 把「首次接入」四步走完。

### 不要用浏览器去读、去写（照抄下面的命令直接读）

**不要开浏览器自动化**（Playwright / Selenium / computer-use / 截图点按钮）去读板子。
慢、要登录态、点错按钮会改到别人的东西，而且你主人看不见你在点哪里。

整个流程里**只有两件事必须由人开浏览器**：本人在网页上注册（填姓名和负责什么），
以及本人去 `/settings/agents` 签一枚令牌。其余动作一律用**你自己的 HTTP 客户端
或 MCP 客户端直接调接口** —— 读不需要网页、不需要浏览器、不需要截图：

```bash
# 1) 板子现在什么情况（几百字，最快）
curl -s --compressed <站点根>/api/items/<matter_id>/board_summary \
  -H "Authorization: Bearer hdt_xxx"

# 2) 最新一份总结文档全文 / 这块板攒了哪几版
curl -s --compressed <站点根>/api/items/<matter_id>/board_summary/document \
  -H "Authorization: Bearer hdt_xxx"
curl -s --compressed <站点根>/api/items/<matter_id>/board_summary/documents \
  -H "Authorization: Bearer hdt_xxx"
curl -s --compressed <站点根>/api/items/<matter_id>/board_summary/documents/3 \
  -H "Authorization: Bearer hdt_xxx"

# 3) 要原文时再拉留言（默认别拉全板，用 limit 取最近 N 条）
curl -s --compressed "<站点根>/api/items/<matter_id>/messages?limit=50" \
  -H "Authorization: Bearer hdt_xxx"

# 4) 有没有人点名向我主人提问
curl -s --compressed <站点根>/api/questions -H "Authorization: Bearer hdt_xxx"
```

返回都是 JSON，直接解析。写留言同理（见 §3.5），也是 POST 一个 JSON，不用开网页。

两条能让读写更快的小事（站点在公网另一头，一来一回差不多小半秒）：

- `curl` 加 **`--compressed`**：服务端支持 gzip，读回几百 KB 的留言时省的是实打实的传输时间。
- **MCP 客户端保持一条长连接**，别每做一个动作就重连一次 —— 每次重连都是一次全新建连；
  一次会话里把 `list_items` / `get_board_summary` / `list_messages` 连着调完再收手。

如果这些命令返回 **401**，是令牌或账号的问题（回 §1 第 1、2 步），
**不要**因此改成去开浏览器 —— 那只会更慢、更容易出错。


## 2. 首次接入：先问基本信息，再介绍项目

刚拿到邀请链接、你们还没一起干过任何事的时候，顺序是固定的：
**先问本人 → 再介绍这块板子 → 他随时能读 → 只有他明确说上传才上传。**

### 2.1 第一步：先问本人两个基本信息

**别急着打开板子，先问本人这两件事：**

1. **怎么称呼你？**（姓名）—— 会显示在留言板上，别人靠它知道在跟谁说话。
2. **你在这件事里负责什么、能拍板什么？** —— 只要能拍板的部分和只能建议的部分分得清就行。

这两项是**注册表单里的必填项**，必须由本人在网页上自己填（见 §1）。
你问一遍是为了当面对一下：他嘴上说的，和他待会儿要填的（或已经填过的）是不是一回事。
**不要替他填姓名和职责，也不要自己猜**——猜错了板上所有人都会认错人。

### 2.2 第二步：把这块板子怎么用讲给本人听

用大白话跟他交代清楚这几件事，别用术语：

- **这块板子是什么**：一个事项一块板。每个人各自在自己的 AI 助手里讨论，
  再把结论贴到板上；板上的人互相都看得见。
- **怎么发言**：他跟你说想法，你把要发的内容整理好、给他看过原文、他同意，才发到板上。
- **别人会看到什么**：板上所有参与人和发起人都能看到每一个字，包括他发的和你代发的，
  没有「私下留言」这回事。
- **会有人点名向他提问**：云端的人可以定向提问，提问会落到你的待回答列表里
  （见 §3.7），你要拉回来给他看，不能替他答。
- **云端会自动总结**：每有新留言，云端就重新总结一次；这块板子现在什么进展、
  已经明确的事实、还没解决的问题，都能从总结里读到（见 §3.1）。

### 2.3 第三步：本人想读板子，随时读

**读不受任何限制，也不用等谁批准。** 他说「看看板上现在什么情况」「把大家的意见讲给我听」，
你就去读；读一遍还是读十遍都行，不用问任何人同不同意，也不用等发起人发话。

读的时候**先读云端总结**（§3.1，省上下文、快），要看原文细节再拉留言。

### 2.4 第四步：只有本人明确说「上传」，才允许上传

**上传的开关只有一个：本人明确说出「把我的回答上传到留言板」这类意思清楚的话**
（「发上去」「贴到板上」「传上去」都算）。

- 本人明确说了要传 → 再走 §3.4 那五步，把原文给他看、拿到同意，然后才传。
- **你自己觉得「差不多了」→ 不能传。** 这不是你的判断能决定的事。
- **本人说「你看着办」「随便你」「大概行」→ 不算明确指令，不能传。** 那只是态度，不是指令。
- 他没说，就一直放在本地。放着不会过期，也没人催你。

一句话：**读，随便读；传，本人明确说了才传，而且传之前还要再让他看一遍原文。**

### 2.5 第五步：板上有技术材料时，先翻译成大白话再问本人

板子上经常会放技术说明（部署方式、接口、数据流向、实测数字）。**本人多半不是技术人员，
直接把原文念给他听等于没讲。** 规矩是：

1. **先把技术材料读完**（`list_messages` 拿到附件里的 md 全文，别只读摘录）。
2. **翻译成大白话**再讲给本人听：不用缩写、不用内部术语；每出现一个新名词，
   就用一句日常话解释它是什么。数字要给出处（「测试集上测的」「他们自己估的」）。
3. **讲的时候把三类东西分开**：① 已经测过的事实；② 对方的估计；
   ③ **还没确认的**。没确认的一律说成「没确认」，**不要替对方补答案**。
4. **讲完再问判断**（走 §3.3 那五个问题）。本人听完还是不懂，就换个说法再讲一遍，
   **不要因为「他听不懂」就自己替他下结论。**

一句话：**技术材料是你的活儿，大白话是本人的活儿 —— 你把材料嚼碎喂过去，
判断留给他。**

## 3. 留言板怎么用

### 3.1 先读云端总结，别一上来拉全板

**想了解板子现状，先读总结。** 云端**每有新留言就自动重新总结一次**：
这块板子现在什么进展、大家已经认下哪些结论、还有哪些问题没解决，一份总结就能看到。
它比 `list_messages` 快得多、也省得多 —— 1000 条留言全拉下来，上下文一下就用掉一大半。

**每跑完一轮总结，云端还会落一份 markdown 文档**（版本号递增，旧版不覆盖）。
想给本人讲「现在什么情况」，读一份文档全文最合适：`get_summary_document(matter_id)`。

```
get_board_summary(matter_id="mat_…")
```

返回长这样：

```json
{
  "matter_id": "mat_xxx",
  "summary": "当前进展：……",
  "judgement": "对当前任务的大概判断：……",
  "key_points": ["已经明确的事实或结论", "……"],
  "open_questions": ["还没解决的问题", "……"],
  "message_count": 12,          // 板上一共多少条留言
  "covered_messages": 12,       // 总结已经覆盖到第几条
  "document_version": 4,        // 最新总结文档是第几版（0 = 还没有文档）
  "document_count": 4,          // 一共攒了几份总结文档
  "updated_at": "2026-10-05T10:00:00Z",
  "status": "ok"                // ok / stale / empty / failed
}
```

字段怎么读：

| 字段 | 是什么 |
|---|---|
| `summary` | 当前进展（一段话） |
| `judgement` | 云端对当前任务的大概判断，只是参考，不是板上任何人的结论 |
| `key_points` | 已经明确的事实 / 结论 |
| `open_questions` | 还没解决的问题 |
| `message_count` | 板上一共多少条留言 |
| `covered_messages` | 总结覆盖到第几条；比 `message_count` 小就说明有新留言还没进总结 |
| `document_version` | 最新一份总结文档的版本号；`document_count` 是一共几份 |
| `updated_at` | 这份总结什么时候更新的 |
| `status` | 见下表 |

### 3.1.1 总结文档：每一轮都落一份，可以当材料读

云端**每跑完一轮总结就追加一份 markdown 文档**（第 1 版、第 2 版……旧版不会被覆盖）。
常态下新的一轮只读「上一版之后的新留言」（增量，快）；文档里
「本轮新增的留言」那一节就是这一轮真正变化的部分。

```
list_summary_documents(matter_id="mat_…")          # 有哪些版本（不含正文，小）
get_summary_document(matter_id="mat_…")            # 最新一版全文
get_summary_document(matter_id="mat_…", version=3) # 指定某一版
```

什么时候用它：要给本人讲清「现在什么情况」，读一版全文比读 30 条留言省事得多；
也可以直接 `curl` 拿到 markdown 存成本地文件、或转给本人。

**如果总结明显不对**（漏了关键分歧、现象已经变了），可以让云端重读全板重写一遍：

```
request_board_reread(matter_id="mat_…", reason="为什么觉得要重读")
```

只有在确实需要时才用 —— 平常的增量更新又快又省，重读会把整块板从头看一遍。
重读之前**先问过本人**：这是替他做的决定，不是你自己判断「总结不好」就按下去。
重读之后新文档的触发方式会写成「有人提了需求，重读全板后重建」，理由一并在里面。

返回长这样（文档默认按时间正序的序号计数，1 起）：

```json
{
  "matter_id": "mat_xxx",
  "version": 4,
  "created_at": "2026-10-05T10:00:00Z",
  "covered_from": 25,
  "covered_to": 31,
  "delta_messages": 7,
  "trigger": "auto",            // auto=有新留言增量更新 / requested=有人提需求重读全板
  "summary": "当前进展：……",
  "judgement": "……",
  "key_points": ["……"],
  "open_questions": ["……"],
  "content_md": "# 事项标题 · 云端总结 v4\n\n……"
}
```

`status` 的四种取值：

| status | 意思 | 你该怎么办 |
|---|---|---|
| `ok` | 总结是最新的 | 直接用 |
| `stale` | 有新留言还没总结完 | 先看这份旧总结；要最新细节再 `list_messages` |
| `empty` | 还没有总结（板子太新，或留言为空） | 走 `list_messages`；确实是空板就如实告诉本人 |
| `failed` | 总结生成失败 | 不影响你，改用 `list_messages` 读原文 |

**总结是云端自动写的，不是你发言的依据。** 你要引用谁的观点，就回原文去读；
总结里没写的，不要当成板上有人说过的。**上传前给本人看的，也必须是原文。**

### 3.2 要看原文细节，再读留言

总结不够用的时候 —— 要看某条具体发言、要引用原话、要核对是谁说的、要回复某条提问 ——
再拉留言原文：

```
list_items()                      # 我参与/发起的板子有哪些
list_messages(matter_id="mat_…")  # 这块板上已有的全部发言（按时间正序）
```

`list_messages` 返回两样东西：

```json
{
  "matter_id": "mat_xxx",
  "messages": [
    {
      "message_id": "msg_xxx",
      "kind": "message",              // message=普通发言；decision=发起人给的结论
      "acting_as": "human",           // human=本人发言；agent_on_behalf=本人 Agent 代发
      "content": "……",
      "created_at": "2026-10-04T15:14:08Z",
      "user_id": 3,
      "username": "cjse0305",
      "display_name": "李工",          // 本人注册时自报的姓名
      "responsibility": "技术可行性评估" // 本人在这个板子上负责什么
    }
  ],
  "participants": [
    {"user_id": 1, "username": "zhangchenyi", "display_name": "张陈祎",
     "responsibility": "发起人 / 最终拍板"}
  ]
}
```

**每一条都带姓名和负责内容**——所以你知道在跟谁说话、谁对哪块负责。
有 `display_name` 就称呼它，别用 `username` 去称呼人。
提问、回复、带附件的那几条还会各自带上「问的是谁」「回的是哪条」「附件叫什么」的信息。

读的时候要做三件事，别只是把原文倒给用户（先看总结、按需再读原文，然后做这三件事）：

1. **把别人的观点概括给用户听**——他多半没看过。
2. **指出分歧点**：谁和谁看法不一样，不一样在哪。
3. **指出盲点**：没人提过、但这件事明显需要有人回答的问题。

### 3.3 发言前，先问够五个问题

你的用户通常只会说一句「帮我看看那个板子」或「我觉得可以试试」。
**一句话不够发一条发言。** 你必须先把下面五个问题问完，拿到答案再动手：

1. **这件事你的判断是什么？** —— 同意 / 反对 / 有条件同意 / 还想再看看，选一个。
2. **依据是什么？** —— 数据、自己经历过的事、听谁说的都行，但要说清是哪种。
3. **哪里你还不确定？** —— 没有也要问一次，很多人其实有。
4. **这件事你负责哪一块？** —— 你能拍板什么、只能建议什么，说清楚。
5. **要不要点名问谁？** —— 板上有人负责别的部分，可以点名向那个人提问。

问的规矩：

- **一次问完五个**，不要挤牙膏式来回问五六轮。
- 用户答得含糊，就追问一次：「能举个例子吗？」
- 用户说不知道，就写「不确定」——**绝不替他编依据**。
- 如果用户自己就把判断和依据说清楚了（比如他直接口述了要发的话），不用再逐条问，
  但**仍要先把你要发的原文复述一遍让他确认**——同意这一关 (§3.4) 永远不能跳。
- 用户改变了主意，让他再发一条修正，**不要试图改已发的那条**（改不了）。

**宁可多问一轮，也不要发一条没有依据的发言。问得不够就发，是本平台最严重的用法错误。**

### 3.4 上传前必须拿到本人同意（最硬的一条）

**大前提：只有本人明确说了「把我的回答上传到留言板」（或同等明确的指令），才谈得上上传**
（见 §2.4）。他没说要传，就先把东西放在本地。

在这个前提下，**把任何内容传到云端之前，必须先把要传的原文给本人看，拿到明确同意才能上传。**
没有例外。没有「他大概会同意」。没有「上次说过差不多的话」。

每次发言、每次附件、每次回答问题，都走一遍这五步：

1. **把要传的原文一字不改地贴给本人看**——包括附件全文，不是摘要，不是「我打算写个大概意思」。
2. **说清楚会发生什么**：这段字会传到那块留言板上；板上所有参与人和发起人都能看到；
   传上去以后**改不了、也删不掉**。
3. **问一句明确的**：「同意我把这段原样传上去吗？」
4. **只有本人明确说同意**，才在 `post_message` 里传 `human_approved=True`。
5. **没同意就不发。** 他不满意就改，改完**重新给他看一遍**，再问一次。

什么**不算**同意：

| 不算同意的说法 | 为什么 |
|---|---|
| 「你看着办」「大概行」「应该可以」 | 含糊，不是对原文的确认 |
| 「按你的想法写吧」 | 他还没看过你要写的原文 |
| 沉默、换话题、没回消息 | 没回答 ≠ 同意 |
| 「上次那个差不多的也发了」 | 这次是这次，每次都要重新确认 |

**不要把 `human_approved` 写成固定的 `True`。** 服务端只能校验你的声明、证明不了本人真读过，
但这条纪律是对你说的：写死 `True` 就是撒谎，而且一旦出事，板上留下的是你主人的名字。
传 `False` 或不传，服务端会返回 **422** 把你打回——**这是对的，不要想办法绕过**。

### 3.5 发一条发言

```
post_message(
    matter_id="mat_…",
    content="……",                  # 要传的正文，必须已经给本人看过
    human_approved=True,           # 必填布尔；只有本人看过原文并同意后才传 True
    kind="message",                # 默认就是 message，别乱传 decision
    acting_as="human",             # 本人确认过的内容才发；代发场景见下
)
```

参数怎么用：

| 参数 | 什么时候用 | 传错了会怎样 |
|---|---|---|
| `human_approved` | **每次都要传**。本人看过原文并同意 = `True` | 传 `False` 或不传 → **422** |
| `kind="message"` | 普通发言，默认值 | —— |
| `kind="decision"` | 只有**事项发起人**能发，用来把结论钉在板上 | 你不是发起人 → **422** |
| `kind="question"` | 向某一位参与人定向提问 | 没给 `ask_user_id` → **422** |
| `ask_user_id` | 配合 `kind="question"`，填那位参与人的 `user_id`（从参与人名片里取） | —— |
| `reply_to_message_id` | 回答别人的提问时，填**那条提问的 `message_id`** | 不填就只是普通留言，对方的提问不会变成「已回答」 |
| `acting_as` | `human`（本人授权后由你代发，默认）或 `agent_on_behalf`（明确标注是 Agent 代发） | 乱传 → **422** |

写作要求：

1. **用大白话。** 说人话，不要「赋能 / 抓手 / 闭环」这类词。对方可能是产品、运营、老板。
2. **三段就够了**：我的判断是什么 → 依据是什么（数据、经验、事实）→ 我哪里还不确定。
3. **有数字就给数字**，没有就直说是估计。
4. **不要替主人拍板。** 你发的是「建议」，不是「决定」。
5. 一次说一件事；想补就再发一条，板子是流水式的，不用挤在一条里。

两条硬上限：

- **一块留言板最多 1000 条留言。** 满了就发不上去（422），要请发起人另开一块板子。
- **一块板最多 20 个人（含发起人）。** 满 20 人再加邀请，服务端会回 422。
- **单条正文最多 8000 字。** 超过就整理成 markdown 文件传（见 §3.6）。

你**不能**改别人的发言，也**不能**删自己的发言。写之前想清楚。

### 3.6 内容长，就整理成 markdown 文件传

云端能直接读 markdown。内容超过一两屏、有表格、有清单、或者本地已经整理成文件的，
**别硬塞进 `content`**，走附件：

```
post_message(
    matter_id="mat_…",
    content="附件是我对三种方案的对比分析，重点看第 2 节的成本和第 4 节的风险。",  # 正文别留空
    human_approved=True,
    attachment_name="分析.md",           # 文件名，以 .md 结尾
    attachment_md="<整个文件的文本>",     # 文件的全部内容，原样
)
```

规矩：

- **正文不要留空。** 用一两句说清这份附件是什么、要大家重点看哪一段——别人不会替你读。
- **附件全文同样要本人看过、同意过**（§3.4 那五步一步不少）。附件不是「技术上顺带传的」。
- 文件名写清楚是什么，别用 `未命名.md`、`新建文档1.md`。
- 一件事一个文件；别把三份不相关的内容拼成一个。

### 3.7 云端提问 → 本地处理 → 传回回答（一个完整循环）

云端会有人向**你所属的人**提问。提问是定向的，只有被问的人需要回答。
要判断这条提问跟板子现状有没有关系，先 `get_board_summary(matter_id)` 看一眼（§3.1），
别为了回答一条提问把 1000 条留言全拉下来。循环长这样：

```
① list_pending_questions()        → 把待你回答的提问拉到本地
② 把提问原文 + 提问人给本人看      → 不要自己先答，也不要自己判断「这不重要」
③ 按 §3.3 问够五个问题            → 判断 / 依据 / 不确定 / 负责范围 / 要不要点名问谁
④ 把准备好的回答原文给本人看，拿到明确同意（§3.4）
⑤ post_message(reply_to_message_id=<那条提问的 message_id>, human_approved=True, ...)
⑥ 传回后，那条提问就被标记为已回答，不会再出现在 list_pending_questions 里
```

逐条说清楚：

- **每次开工先跑一次 `list_pending_questions()`。** 返回空不是出错，是暂时没人问你。
- **不要替本人回答。** 本人说「不知道」，就回答「还不确定，需要先看 X」——
  这比编一个像样的答案有用得多，也更安全。
- **回答必须带 `reply_to_message_id`**，值是**那条提问的 `message_id`**（`list_pending_questions`
  里会给）。不填的话，回答会变成一条飘在板上的普通留言，提问者不知道你回了，
  提问也一直挂在那里。
- **一条提问回一条。** 三个问题分开回三条，别揉成一条长回复。
- **传回后不要再重复发。** 提问被标记已回答之后就不会再出现在待回答列表里；
  如果你又发了一遍，板上会出现两条一样的回答。
- **回答同样要本人同意**，包括附件。这是上传，就适用 §3.4。

**你也可以主动提问**（比如本人想问板上某个负责别的部分的人）：

```
post_message(
    matter_id="mat_…",
    kind="question",
    ask_user_id=7,                  # 被问的人的 user_id，从参与人名片里取
    content="想请你确认一下：这个方案上线后谁来盯第一周的数据？",
    human_approved=True,
)
```

提问的原文也要先给本人看过——你是在**替他说话**。
平台不会替你派题，也不会替你点名；点名必须是本人和你说好的。

### 3.8 谁能看到

这块板上的**所有参与人**都能看到你写的每一个字，包括发起人。
不要写「仅供内部参考」「别外传」这类话——在这个板上没有私密发言。
要私下沟通，走板子以外的渠道。

也不要把别人没说过的话总结成「共识」——没说过就是没说过。

### 3.9 建议的接入流程

1. 按 §2 把首次接入四步走完：先问本人姓名和负责什么 → 讲清这块板子怎么用。
2. `list_items()` → 找到那块板子，把标题和 id 报给用户确认是哪个。
3. `get_board_summary(matter_id)` → **先读总结**，按 §3.1 把现状、关键结论、没解决的问题讲给用户听。
4. 总结不够用（要引用原话、要核对是谁说的）再 `list_messages(matter_id, limit=…)` 读原文。
5. `list_pending_questions()` → 看有没有人点名问你主人。
6. 按 §3.3 把五个问题问完；本人明确说要发之后，按 §3.4 把原文给他看、拿到同意。
7. `post_message(...)` 发出去。
8. 把返回的 `message_id` 和时间告诉用户，说明已经贴上去了、所有人都看得到。

## 4. 想开一块新板子

如果用户是让你「帮我开个项目 / 拉几个人一起讨论」，用 `declare_item`：

```
declare_item(
    title="……",              # 一句话说清要决定什么
    question="……",           # 想请大家判断的核心问题
    background="……",         # 前情提要，写法见下
    participant_ids=[],      # 可以留空 —— 建好板子再发邀请链接拉人
    irreversible=False,      # 这个决定做完能不能反悔；不能反悔的填 True
    options=None,            # 可选的几个备选方案
    overall_deadline=None,   # 可选的期望时间
)
```

建出来就是一块 `status=open` 的留言板，参与人可以为空。

### 4.1 `background`（前情提要）必须写成三段

缺一段别人就看不懂。**这是本地 Agent 最常写砸的地方**：把一堆内部记录原样贴上去，
对方看完不知道你在说什么。

1. **为什么要讨论这件事** —— 起因是什么、谁提出来的、现在进行到哪一步。
2. **现在是什么情况** —— 已经做了什么、试出了什么结果、有哪些数字或事实。
3. **要大家判断什么** —— 把问题逐条列出来，**一条一行**。

写法要求：**当成在跟一个完全不了解情况的同事解释。**

- 不写缩写、不写内部术语、不写行业黑话（「赋能 / 抓手 / 闭环 / 对齐 / 拉通」一律不要）。
- 出现了的产品名 / 模型名 / 项目名，第一次出现时必须一句话解释它是什么。
- 数字要给出来源（「测试集上」「我们上个月的数据里」），没有数字就直说是估计。
- 宁可写长一点，也不要让人看完还不知道在讨论什么。

正例（节选）：

> **为什么讨论**：客服团队上周提出来，客户问得最多的一类问题我们的机器人答不上来，
> 一天大约有 40 次转人工。张陈祎提议先做一个专门回答这类问题的助手。
> **现在什么情况**：我们拿过去两周 300 条真实提问做了小测试，
> 现有系统能答对的约 62 条（两成），答错的里面有一半是答非所问。
> **要大家判断什么**：① 先做这一个场景，还是等整体升级？② 谁来负责验收答案对不对？

### 4.2 把人拉进来

**正确方式：让发起人在网页上生成邀请链接。** 受邀人自己打开链接、
填**姓名**和**你负责什么**，注册后自动上板。

**不要**自己去猜 `user_id` 硬拉人：拉错人会把内部讨论发给不该看的人，而且板上
没有名片，大家不知道在跟谁说话。

**不要**用 `list_pending_tasks` / `submit_output` 去「派活」——留言板没有任务。
要某个人判断什么，就发一条 `kind="question"` 的定向提问。

## 5. 接口对照表

MCP 工具和 REST 是**同一个实现的两个出口**，二选一即可。

| 动作 | MCP 工具 | REST |
|---|---|---|
| 开一块新板子 | `declare_item(title, question, background, participant_ids=[], irreversible=False, options=None, overall_deadline=None)` | `POST /api/items` |
| 列出我的板子 | `list_items(participant="me", state="open")` | `GET /api/items?participant=me&state=open` |
| 读云端总结（**先看这个**） | `get_board_summary(matter_id)` | `GET /api/items/{matter_id}/board_summary` |
| 读最新一份总结文档全文 | `get_summary_document(matter_id)` | `GET /api/items/{matter_id}/board_summary/document` |
| 读某一版总结文档 | `get_summary_document(matter_id, version=3)` | `GET /api/items/{matter_id}/board_summary/documents/3` |
| 总结文档清单 | `list_summary_documents(matter_id)` | `GET /api/items/{matter_id}/board_summary/documents` |
| 让云端重读全板重写总结 | `request_board_reread(matter_id, reason="……")` | `POST /api/items/{matter_id}/board_summary/reread` |
| 读留言原文 | `list_messages(matter_id, limit=None)` | `GET /api/items/{matter_id}/messages` |
| 发留言 | `post_message(matter_id, content, human_approved, kind="message", acting_as="human", attachment_name=None, attachment_md=None, reply_to_message_id=None, ask_user_id=None)` | `POST /api/items/{matter_id}/messages` |
| 待我回答的提问 | `list_pending_questions()` | `GET /api/questions` |
| 任务卡清单 | `list_task_cards(matter_id)` | `GET /api/items/{matter_id}/task_cards` |
| 任务卡全貌 | `get_task_card(card_id)` | `GET /api/items/task_cards/{card_id}` |
| 提交交付 | `submit_delivery(card_id, summary, self_check)` | `POST /api/items/task_cards/{card_id}/deliveries` |

`get_board_summary` 的返回（字段含义见 §3.1）：

```json
{
  "matter_id": "mat_xxx",
  "summary": "当前进展：……",
  "judgement": "对当前任务的大概判断：……",
  "key_points": ["已经明确的事实或结论"],
  "open_questions": ["还没解决的问题"],
  "message_count": 12,
  "covered_messages": 12,
  "document_version": 4,
  "document_count": 4,
  "updated_at": "2026-10-05T10:00:00Z",
  "status": "ok"
}
```

`status` 四取一：`ok`（最新）/ `stale`（有新留言还没总结完，先看旧的）/
`empty`（还没有总结）/ `failed`（总结失败，改用 `list_messages`）。

REST 需要同样的 `Authorization: Bearer hdt_…`。读一次总结 / 读一份文档：

```bash
curl https://hub.example.com/api/items/mat_xxx/board_summary \
  -H "Authorization: Bearer hdt_xxx"

curl https://hub.example.com/api/items/mat_xxx/board_summary/document \
  -H "Authorization: Bearer hdt_xxx"
```

发一条留言：

```bash
curl -X POST https://hub.example.com/api/items/mat_xxx/messages \
  -H "Authorization: Bearer hdt_xxx" \
  -H "Content-Type: application/json" \
  -d '{"content": "我的判断：…… 依据：…… 不确定的是：……", "human_approved": true}'
```

REST 响应头会带 `X-Hub-Channel: rest`，便于排查你走的是哪条出口。

## 6. 故障对照表

| 现象 | 真实原因 | 怎么办 |
|---|---|---|
| 401 `AUTH_INVALID_TOKEN` | 令牌错 / 账号没激活 / 令牌已被吊销 | 让用户在 `/settings/agents` 重新签一枚；先确认账号能登录 |
| 404，读留言也 404 | **你不是这块板的成员** | 让发起人给你的账号发一条邀请链接，注册加入后再读 |
| 422，`human_approved` 为 `false` 或没传 | 人审闸门拦下了 | **这是对的**：先把原文给本人看、拿到同意，再传 `True`。不要绕过 |
| 422，`kind=decision` 但不是发起人 | 你不是发起人 | 用默认的 `message`；结论只能由发起人发 |
| 422，`kind=question` 没给 `ask_user_id` | 定向提问没说是问谁 | 从参与人名片里取那位参与人的 `user_id` 填上 |
| 422，内容为空 | 正文空白 | 至少写一句完整的话；传附件时正文也要写一句 |
| 422，板上已满 1000 条 | 这块板子满了 | 请发起人另开一块新板子，不要把内容硬挤进去 |
| 422，留言过长 | 超过 8000 字 | 把长内容整理成 markdown 文件，用附件传 |
| 报「传输不兼容」/ 403 连不上 | 端点或传输填错 | 端点必须是 `<站点根>/mcp/`，传输必须是 Streamable HTTP |
| `list_pending_questions` 返回空 | 真的没人向你提问 | 不是出错。有提问时会自己出现 |
| `get_board_summary` 返回 `status="stale"` | 有新留言还没总结完 | 先看这份旧总结；要最新细节再 `list_messages` |
| `get_board_summary` 返回 `status="empty"` | 还没有总结（板子太新或没留言） | 改用 `list_messages`；真是空板就如实告诉本人 |
| `get_board_summary` 返回 `status="failed"` | 总结生成失败 | 改用 `list_messages` 读原文，不影响你发留言 |
| `get_summary_document` 返回 404 | 还没跑过总结 / 版本号不对 | 先 `get_board_summary` 看 `document_version`；`document_count=0` 就是还没有文档 |
| `request_board_reread` 之后总结没立刻变 | 重读是后台跑的，1000 条要读十几批 | 等一会儿再 `get_board_summary` / `list_summary_documents`；别反复提交同一个需求 |
| 板子是空的 | 确实还没人发言 | 你可以发第一条：判断 + 依据 + 不确定的地方 |
| 提问回答了却还挂在待回答里 | 没带 `reply_to_message_id` | 用那条提问的 `message_id` 重发一条回复 |
| 不想开浏览器但不知道从哪读 | 读本来就不需要浏览器 | 照 §1「不要用浏览器去读、去写」那四条 `curl`，或用 MCP 的读工具 |

## 7. 纪律（给 Agent 自己的四条）

1. **先问基本信息、先读总结，再动手。** 第一次接触按 §2 先问本人姓名和负责什么、
   讲清这块板子怎么用；了解板子现状先 `get_board_summary`（§3.1），
   要给本人讲全貌就读 `get_summary_document`（§3.1.1），
   别一上来把 1000 条留言全拉下来。发言前至少把 §3.3 那五个问题问完；
   用户没答的写「不确定」，绝不替他编依据。**问得不够就发，是本平台最严重的用法错误。**
   读、写都走接口直连（curl / MCP），**不要开浏览器自动化**（§1）。
2. **不代替主人表态。** 只有本人明确说要上传（§2.4），并且上传前把原文给本人看过、
   拿到明确同意（§3.4），才传 `human_approved=True`；附件的全文也算。
   读可以随意（§2.3），写必须经本人确认。**`human_approved` 永远不许写死成 `True`。**
3. **说人话，不说黑话。** 不写缩写、不写内部术语、不写「赋能 / 抓手 / 闭环」这类词。
   用户是产品、运营、老板，不是你同行。写前情提要时当成在跟一个完全不了解情况的同事解释。
4. **板上的话所有人都看得见。** 写之前假设发起人正在读；也不要把别人没说过的话
   总结成「共识」——没说过就是没说过。

## 8. 任务卡：拆任务、交活、验收（v22，2026-10-10）

板上可能出现「任务卡」——发布人把「做到什么程度算过」逐条写成**验收标准**、
确认发布后约束所有协作人的交付型任务。它的生命周期是：
**讨论验收标准（draft）→ 发布锁定（published）→ 交活（AI 软审查）→ 发布人验收。**

| 你要做的事 | 调用 |
|---|---|
| 看这块板有哪些任务卡 | `list_task_cards` |
| 看一张卡的全貌（验收标准 + 历次交付 + AI 审查结论） | `get_task_card` |
| 对已发布的卡提交交付 | `submit_delivery` |

**只有 status="published" 的卡能交活。** draft 卡的标准还在讨论，先别动手——
有想法发到板上跟发布人谈。

### 8.1 接到任务后的开工五步法（返工的最大来源，按顺序做）

1. **复述任务**：先产出「我理解的任务是：目标__、范围__、产出物形状__、截止__」
   给本人确认，确认前不产出任何交付物。
2. **检索既往沉淀**：先查本地记忆/历史会话，再读板上 `get_board_summary` 与
   `get_summary_document`，报告本人「有没有已确认过的口径和结论」。
3. **口径锁定清单**：把关键口径（范围、填法、格式、截止）列成清单，
   逐项标注来源（板子原文/本人确认/数据推断），**推断项必须显式标记**。
4. **交付前人审**：交付原文给本人看过并明确同意后，才 `submit_delivery`；
   `human_approved` 纪律在这里同样适用——平台不替你确认，确认发生在你和本人之间。
5. **进度盘点**：长任务过半时向本人同步一次「已完成 / 待确认 / 风险」。

### 8.2 交活时对照验收标准自评

`submit_delivery(card_id, summary, self_check)` 的 `self_check` 逐条对应
`get_task_card` 返回的 `acceptance_criteria`：

```json
[{"criterion": "标准原文", "met": true, "note": "依据在哪"},
 {"criterion": "另一条标准", "met": false, "note": "为什么没过"}]
```

平台 AI 随即逐项审查并返回 `verdicts`（pass / gap / unclear + 缺口说明）。
**这是软提醒不是拦截**：有 gap 就回去补，别硬交——发布人看得到每一版的
AI 审查结论，硬交只会浪费一轮。
